# COPY и планы чтения PostgreSQL

Сценарий измеряет операции, которые связывали этапы нативного конвейера через БД, запрос первой страницы фактов и переход к заявкам. В качестве примера взят завершённый прогон на 120 заявках, из которых 100 попали в проверяемый пакет. В базе было два прогона того же размера. У пользовательских таблиц уже работал autoanalyze.

| Вариант SELECT | Строки результата | План | Shared hit | Temp read/write, блоков | Время выполнения |
|---|---:|---|---:|---:|---:|
| normalized_values, пакет 100 | 28 349 | Parallel Seq Scan, sort, Gather Merge | 3 854 | 454 / 454 | 88,901 мс |
| comparison_values, пакет 100 | 14 372 | Bitmap Index Scan comparison_path, Bitmap Heap Scan, sort | 1 374 | 845 / 846 | 59,887 мс |
| comparison_values, весь запуск | 17 214 | Parallel Seq Scan, sort, Gather Merge | 2 769 | 1 013 / 1 014 | 68,295 мс |
| aggregate_facts, первые 100 | 100 | Seq Scan, top-N heapsort | 2 216 | 0 / 0 | 15,670 мс |
| aggregate_members, первые 100 по одному факту | 1 | Index Only Scan, aggregate_members_pkey | 4 | 0 / 0 | 0,239 мс |

Приведена строка Execution Time из EXPLAIN. TIMING OFF выключает часы каждого узла, сохраняя общее время выполнения. Время включает работу сервера PostgreSQL. Передача JSON клиенту, преобразование jsonb в текст для обычной выборки, декодирование JsonCpp и отрисовка в браузере требуют отдельных замеров. Основные страницы уже находились в shared buffers. При холодном старте или другом числе параллельных запусков планы могут отличаться.

Первые три SELECT читают значительную долю данных. Ключи normalized_values и comparison_values уже начинаются с run_id, app_id. Для 100 из 120 идентификаторов PostgreSQL выбрал последовательное и bitmap-чтение, а часть отсортированных записей записал во временные файлы. Потоковая передача текущего пакета следующему этапу позволяет полностью убрать запрос вместе с передачей и повторным разбором. Новый индекс с тем же префиксом добавил бы работу при каждом COPY.

У aggregate_facts идентификатор группы хранится как текст. ORDER BY fact_id::bigint сохраняет естественный порядок 1, 2, …, 10. Для исходной страницы PostgreSQL прочёл все 13 696 фактов прогона и выбрал 100 чисел через top-N. На этом стенде измерение заняло 15,670 мс. Если на больших объёмах замер покажет неприемлемую задержку этой выборки, можно отдельно проверить индекс по (run_id, (fact_id::bigint)) и измерить его влияние на запись. Для drill-down существующий составной ключ дал ноль heap fetches. Схема и набор индексов для этого изменения сохранены.

В том же прогоне поля APP_IDS в aggregate_facts содержат 34 428 идентификаторов, занимающих 447 564 байта в текстовом JSON PostgreSQL. В aggregate_members находятся те же 34 428 связей. Байты текстового JSON не равны размеру сжатого jsonb на диске. Встроенный список используется при выдаче и выгрузке полного объекта факта, отдельная таблица поддерживает индексированный постраничный drill-down. Сохранены обе формы. Запись добавляет FACT_ID и id к уже сформированному объекту, не копируя массив приложений в ещё один объект C++.

## Повторение на своей базе

Из корня проекта для стандартного Compose:

~~~sh
docker compose exec -T postgres psql -X -U lens -d lens < scripts/profile-storage.sql
~~~

По умолчанию скрипт находит крупнейший завершённый прогон. Для выбора определённого передайте psql параметр, например -v run_id=идентификатор. Нужен завершённый прогон хотя бы с одной заявкой и одним фактом. Скрипт открывает READ ONLY REPEATABLE READ и завершает измерения ROLLBACK. Текст результата включает полный план, число выданных строк, страницы в кэше и временных файлах, актуальность статистики, размеры таблиц и индексов по всем запускам, число членов фактов для выбранного запуска. Для сравнения стендов фиксируйте число запусков в базе, число строк и условия прогрева.

## Поля профиля записи

CopyProfile ведёт локальные счётчики одного потока исполнения. Чтобы включить счётчики, задайте LENS_PROFILE=1 в окружении процесса backend перед его стартом. После завершения запуска метрики доступны в поле summary.profile.storage.

| Поле | Что измеряется |
|---|---|
| transactions | Успешные транзакции записи нормализованных строк, сравнений, разрезов, фактов, связей и проверок |
| connection_seconds, begin_seconds, commit_seconds | Открытие подключений этих транзакций, создание транзакций и commit |
| tables.<имя>.streams, rows | Число операций COPY и строк, отправленных через libpqxx |
| json_bytes | Суммарный размер закодированных JSON-объектов в UTF-8 до экранирования COPY и формирования PostgreSQL jsonb. У aggregate_members нет JSON-колонки, поэтому значение равно нулю |
| open_seconds | Открытие COPY для таблицы |
| prepare_seconds | Остаток времени цикла после вычета сериализации JSON и вызовов записи. Здесь находятся выбор полей, присвоение ID и накладные расходы самих измерений |
| serialize_seconds | Подготовка компактного JSON в воспроизводимом UTF-8 представлении |
| write_seconds | Преобразование полей COPY и отправка через libpqxx, включая ожидания при заполнении буфера |
| complete_seconds | Завершение COPY и ожидание ответа PostgreSQL |

Сумма вложенных таймеров представляет компоненты storage_seconds. Повторное прибавление её к времени всего запуска завышает результат. WAL, обновление индексов и проверка внешних ключей происходят внутри PostgreSQL и могут перекрываться с записью клиента. По одному complete_seconds нельзя определить их изолированную стоимость. У API-журнала, обновлений статуса, чтения SQL и отдачи выгрузки свои пути исполнения. В данном профиле учитываются только транзакции массовой записи.

При обычном запуске выбирается отдельная компилируемая ветвь COPY без часов и счётчиков на каждой строке. Выбор происходит один раз на транзакцию. Измерения по строкам нужны для диагностики. Чтобы оценивать скорость для пользователя, сравнивайте отдельные полные прогоны с выключенным профилированием.

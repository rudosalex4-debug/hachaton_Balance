# Проверка реализации

## Проверочный стенд

Intel Core i5-8300H (4 ядра / 8 потоков), WSL2 с ~7.7 GiB памяти, Docker Engine; Ubuntu 24.04, GNU g++ 13.3, CMake 3.28, PostgreSQL 16, libpqxx 7.8.1, simdjson 3.6.4, JsonCpp 1.9.5, Python 3.12.3. Датасет расположен на диске D: и подключён через /mnt/d. База находится в именованном Linux-томе Docker.

В среде уже был локальный образ Ubuntu с зависимостями. Недостающие dev-пакеты взяты из официального репозитория Ubuntu. Полный функциональный стенд запущен на локальных образах: исходный backend собран g++/CMake, frontend — production dist, worker — Python 3.12. Скачивание чистых базовых образов из Docker Hub в этом WSL завершилось сетевым тайм-аутом; установка с нуля требует доступной сети.

CMake автоматически определяет ABI исключений libpqxx. Для пакета Ubuntu 7.8, собранного без std::source_location, используется локальный заголовок совместимости; стандарт основного приложения остаётся C++20.

## Фактически выполненные проверки

- Production-сборка React/TypeScript/Vite прошла. Monaco загружается отдельным chunk; предупреждение о его размере не препятствует сборке.
- Browser smoke в headless Edge с подменённым API: сохранение конфигурации и Python-кода, загрузка Monaco, загрузка папки, факт → заявка → сравнение, переключение всех атрибутов и мобильная ширина 390 px. Ошибок JavaScript не обнаружено. Это UI-проверка отдельно от интеграционных тестов реального API.
- В контейнере Python 3.12 прошли все 18 unit-тестов worker, включая реальную Linux Landlock/seccomp-песочницу.
- C++ CTest: 28 тестов прошли общим запуском; отдельный полный тест затем успешно обработал все 2 002 пары. Итого подтверждены все 29 тестов.
- Реальный HTTP API + PostgreSQL + isolated worker: загрузка/валидация, одинаковые результаты C++ и трёх Python-шаблонов, distinct counts, drill-down, SQL-группировка, повторяемость, два параллельных пользователя, исключения, тайм-ауты и отмена — успешно на итоговом C++ backend.

Дополнительно реальный Python-агрегатор обработал NDJSON объёмом 418 638 918 байт под Linux Landlock/seccomp с лимитом памяти 1 024 MiB. Все 44 588 фактов точно совпали с PostgreSQL; время проверки и выполнения после подготовки входа — 93.099 с. Большие входы представлены ленивыми Sequence, а не удерживаются одновременно в памяти.

## Полный датасет

Результаты проверяются по независимому алгоритму `tests/reference_oracle.py`, не импортирующему приложение. Полный HTTP-прогон сравнивает итоговые счётчики с этими значениями.

| Показатель | Проверочное значение |
|---|---:|
| Пар заявок | 2 002 |
| Нормализованных BEFORE | 285 698 |
| Нормализованных AFTER | 286 523 |
| Строк UNION | 572 221 |
| Строк сравнения | 289 533 |
| SAME | 275 121 |
| VALUE_CHANGED | 7 567 |
| ATTRIBUTE_NEW | 3 835 |
| ATTRIBUTE_LOST | 3 010 |
| Изменившихся заявок | 502 |
| Смен итогового решения | 385 |
| Материализованных фактов (default dimensions) | 44 588 |

Числа не зашиты в расчёт: они используются только в тестовых утверждениях. Другая конфигурация закономерно меняет результаты.

## Замеры полного цикла

| Вариант | Полный цикл |
|---|---:|
| До оптимизаций, входы через /mnt/d | 534.346 с |
| После оптимизаций, входы через /mnt/d | 339.025 с |
| После оптимизаций, входы в Linux-томе | 322.820 с |

Последний замер включает чтение, все три этапа, COPY, индексы PostgreSQL и сохранение фактов. По этапам: чтение 1.457 с; разрезы 10.162 с; нормализация 109.109 с; сравнение 93.441 с; агрегация 108.442 с. Из этого сохранение в БД заняло 183.180 с (включено в этапы).

**Ограничение: целевые 30 секунд полного цикла не достигнуты. Предел 5 минут также превышен на данном стенде примерно на 23 секунды. Функциональная корректность подтверждена; полное соответствие требованиям производительности не заявляется.** Для дальнейшего ускорения главный оставшийся участок — сохранение и чтение JSON-витрин в PostgreSQL.

Отдельный C++ эталонный тест нормализации/сравнения 2 002 пар из Linux-тома прошёл за 22.388 с. Это не полный цикл: в нём нет PostgreSQL и агрегации. Дополнительные запуски не выполнялись одновременно с финальным end-to-end замером; состояние ОС/дисковых кэшей не контролировалось, поэтому небольшие различия времени не следует трактовать как отдельное ускорение.


Время storage входит в соответствующие этапы; его нельзя повторно суммировать. `core_benchmark` измеряет только ядро без PostgreSQL и HTTP и не заменяет end-to-end замер. Цель 30 секунд не объявляется достигнутой без подтверждающего полного замера. Для снижения стоимости файлового доступа в WSL желательно хранить рабочие данные в Linux-файловой системе; исходная поставка сохраняется в указанной пользователем папке Windows.

## Расхождения в учебном эталоне

Фактические CSV содержат шесть различий, хотя один исходный README говорит о пяти. Эталонный тест использует 12 BEFORE / 14 AFTER / 26 UNION / 14 comparison / 6 changed.

В учебных CSV присутствуют синтетические части PATH `scoreCard`, `Limit`, `reason.code`, которых нет в исходном JSON. В тесте эти три обозначения явно сопоставлены с реальными JSON-путями, также сопоставлены подписи бакетов вида `100K`. Приложение сохраняет канонический путь по входному JSON, не добавляя фиктивных узлов. Значения каждой строки учебного сравнения проверяются, кроме такого документированного преобразования обозначений.

## Повторение проверок

```bash
bash scripts/build-wsl.sh
# Полный отдельный C++ эталон:
LENS_DATASET="$PWD/data/RUN-20260827-0001" \
  backend/build/core_tests --gtest_filter=Reference.FullProvidedDataset
python3 tests/reference_oracle.py
python3 tests/integration_api.py --url http://localhost:8088 --full
# После появления завершённого полного прогона:
python3 tests/integration_worker_large.py --compose docker-compose.yml
```

API-тесты создают отдельные аккаунты и сохраняют тестовые прогоны для диагностики. Пользовательские данные они не удаляют. Ошибочные/отменённые прогоны не публикуют частичные результаты; сервер остаётся доступен.

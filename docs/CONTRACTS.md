# Контракты и архитектура

## Конвейер и данные

C++ выполняет асинхронные этапы и сохраняет их результаты в PostgreSQL. Статус запуска: `queued`, затем `running` с этапами `validating`, `normalizing`, `comparing`, `aggregating`, `checking`, затем `completed`, `failed` или `cancelled`. Детальные результаты и отчёты доступны только после `completed`; повторный запуск всегда получает новый идентификатор. Незавершённые прогоны после рестарта помечаются ошибкой.

Нормализованные строки содержат `APP_ID`, `SOURCE`, `PREFIX`, `CLASS`, `SUFFIX`, `ARRAY_KEY`, `KEY`, `PATH`, `VALUE`, `VALUE_TYPE`, `ADJUSTED_VALUE`. Обе стороны сохраняются вертикально — это технический UNION. `VALUE_TYPE` различает NULL/BOOLEAN/NUMBER/STRING; значения сериализуются строками, включая `NULL`, `true`, `false`. Канонические числа сравниваются точно. Бакеты применяются только к группировке.

Строка сравнения содержит идентичность `(APP_ID,PATH,ARRAY_KEY)`, `VALUE_BEFORE/AFTER`, `ADJUSTED_BEFORE/AFTER`, `TYPE_BEFORE/AFTER`, `PRESENT_BEFORE/AFTER`, `DIFF_FLAG`, `CHANGE_TYPE`. Признаки присутствия отличают отсутствие от null и пустой строки. Изменения: SAME, VALUE_CHANGED, ATTRIBUTE_NEW, ATTRIBUTE_LOST.

Массивы настраиваются в `array_rules` по каноническому пути: `mode: field` с `fields`, `mode: value` и `mode: index`. Для value возможна политика повторов `allow_duplicates: true`. Компоненты вложенных ключей соединяются `|`, составные поля одного элемента — `~`; разделители и управляющие символы экранируются. Типы ключей сохраняются: строка `"1"` не смешивается с числом `1`. Обычный ключ правила `AGELOW@21` остаётся совместим с исходными проверками. Ключи должны быть уникальны; некорректные идентификаторы не перезаписываются молча.

`ApplicationSegment` содержит обязательные поля разрезов. `PRODUCTS` — строка названий через `;`. При нескольких продуктах одиночные поля моделей/порогов/причин объединяют отсортированные уникальные значения через `;`; это описательный набор, а не выбор «главного» продукта. `PRODUCT_CONTEXT_BEFORE/AFTER` сохраняет отдельные записи продуктов и их исходные типизированные атрибуты. TOP_OFFER определяется по доступным предложениям и их рангу.

Факты содержат выбранные измерения, `CNT` и `APP_IDS`; CNT равен числу уникальных заявок. В PostgreSQL материализуется связь aggregate_members. Поле значения факта называется `VALUE_ADJUSTED` (в нормализации — `ADJUSTED_VALUE`). Дополнительные группировки выполняются SQL по сохранённым comparison_values и application_segments без чтения исходных JSON.

## Python API

```python
def normalize(records, config, emit): ...
def compare(union_rows, config, emit): ...
def aggregate(comparison_rows, union_rows, segments, config, emit): ...
```

Каждая функция вызывает `emit(dict)` для каждой выходной записи и возвращает `None`. Нормализатор получает `APP_ID`, `SOURCE`, текст JSON в `raw` и разобранный объект `document`. Для XML и CSV адаптер сначала формирует JSON по профилю из манифеста. Десятичные числа в `document` читаются с `Decimal`. Сравнение получает вертикальный union; начальные разрезы доступны через `config['application_segments']`. Для замены разрезов emit должен передать запись с `record_type: 'segment'`; вернуть нужно все заявки текущего пакета. Без таких записей сохраняются стандартные разрезы.

В агрегаторе `comparison_rows` и `union_rows` — читаемые последовательности (`collections.abc.Sequence`) с ленивым чтением NDJSON. Поддерживаются `len()`, индексация (включая отрицательные индексы), срезы и повторный/вложенный обход. Это позволяет обработать полный набор в ограничении памяти без загрузки всех строк сразу. Каждое чтение возвращает отдельный словарь: изменения прочитанной строки не изменяют входную последовательность. Срез или явный `list(rows)` материализует выбранные строки и расходует память процедуры. `segments` остаётся списком. Контракты входных списков нормализатора и сравнения и формат `emit(dict)` не меняются.

Код, SHA256, параметры процедур и конфигурация фиксируются в снимке запуска. SHA256 фактического датасета сохраняется после валидации. Изменение исходных файлов меняет fingerprint и результат; для воспроизведения нужны те же входные файлы, а не только тот же путь. Встроенные процедуры доступны как `normalize/compare/aggregate` (C++) и `python-normalize/python-compare/python-aggregate`.

Пакеты передаются NDJSON через отдельную директорию задания. Metadata: `{type:'meta',kind,config}`, далее `{type:имя_набора,data:строка}`. C++ валидирует схему, типы, идентичности и связь с заявками до публикации. stdout/stderr попадают в журнал; ошибки не завершают HTTP-сервер. Регистрация нормализатора, сравнения и агрегатора проверяет AST и интерфейс без исполнения тела модуля. При регистрации проверки модуль загружается в Linux-песочнице для проверки объекта CHECK и чтения его параметров; функция проверки при этом не вызывается.

Параметры: `worker_timeout_seconds` 1–900 (по умолчанию 180), `worker_memory_mb` 128–1536 (по умолчанию 1024). Выход ограничен 512 MiB, 5 млн записей, 16 MiB на запись. Супервизор завершает процесс при тайм-ауте/отмене. Worker не имеет сети, capabilities и writable root; Linux Landlock ограничивает файлы, seccomp — системные вызовы. При отсутствии поддержки изоляции исполнение отклоняется.

## HTTP API

Все прикладные маршруты имеют префикс `/api/v1`. Регистрация/вход создаёт HttpOnly SameSite=Strict cookie. Конфигурации, загруженные наборы, пользовательские процедуры и запуски принадлежат пользователю; встроенные ресурсы общие и доступны для создания своей копии. API проверяет владельца до выдачи результатов.

| Метод и маршрут | Назначение |
|---|---|
| POST /register, /login; POST /logout; GET /me | Сессия пользователя |
| GET /defaults | Стандартные настройки |
| GET /datasets; POST /datasets | Список / регистрация `{name,path}` |
| POST /datasets/upload | `{name,files:[{path,content}]}`, манифест и ответы JSON/XML/CSV в UTF-8. До 48 MiB содержимого, до 8 MiB на файл |
| GET /procedures; GET /procedure-templates | Процедуры и исходные Python-шаблоны |
| POST /procedures; GET/PUT /procedures/{id} | Создание/чтение/изменение процедуры |
| POST /configs; GET /configs; GET/PUT /configs/{id} | Сохранённые конфигурации |
| POST /runs | `{config_id}` → новый запуск |
| GET /runs; GET /runs/{id}; GET /runs/{id}/logs | Состояние и журнал |
| POST /runs/{id}/cancel | Отмена |
| GET /runs/{id}/normalized, /comparison, /segments, /facts | Страницы результатов |
| GET /runs/{id}/facts/{factId}/apps | Страница заявок факта |
| GET /runs/{id}/apps/{appId} | Разрез и страница сравнений заявки |
| POST /runs/{id}/query | SQL-группировка |
| POST /runs/{id}/query/apps | Исходные заявки динамической группы |
| GET /runs/{id}/checks | Общая таблица проверок, фильтры result/confidence/check_id |
| GET /runs/{id}/report | Сводка прогона, числа PASS/FAIL/LOW, сведения о проверках и ссылки |
| GET /runs/{id}/export?artifact={artifact}&format={format} | Полная таблица завершённого прогона. `artifact` принимает `normalized`, `comparisons`, `facts` или `checks`. Форматы `json`, `xml` и `csv` |
| GET /runs/{id}/report.html | Самостоятельный HTML с полным набором строк проверок и ссылкой в приложение |

При регистрации набора сервер применяет `manifest.input_profiles` ко всем ответам соответствующего расширения. Поле `input_contract` в описании набора содержит версию и профили преобразования. Поле `input_formats` содержит количество файлов каждого формата. Исходный и преобразованный ответ ограничены 8 MiB, набор на сервере — 512 MiB до и после преобразования. Примеры профилей и схемы выгрузок описаны в [руководстве по форматам](FORMATS.md).

Страницы используют `offset` и `limit` (1–1000), возвращают `items`, `total`, `offset`, `limit`. Детали заявки возвращают `comparison`, `segment`, `total`, `offset`, `limit`. Фильтры диагностических данных: `app_id`, `path`, `array_key`, `source`, `diff_flag`, `change_type` (точное совпадение).

Пример SQL-запроса: `{ "dimensions": ["SOURCE", "PRODUCTS"], "filters": {"DIFF_FLAG":1}, "offset":0, "limit":100 }`. Для drill-down передать `/query/apps` те же filters, дополненные значениями выбранной группы. Поддерживаются поля витрины и обязательные скалярные разрезы; произвольный SQL не принимается.

`summary.timings` содержит read_seconds, segments_seconds, normalize_seconds, compare_seconds, aggregate_seconds, checks_seconds и storage_seconds. Время storage входит также в соответствующие этапы, поэтому его нельзя повторно суммировать с ними. `total_seconds` включает весь конвейер и сохранение результатов.

## Проверки — этап 4

Проверка сохраняется через `/procedures` с `kind: "check"`. Конфигурация содержит `checks: [{"procedure_id": "...", "params": {}}]` (до 20 разных процедур); отсутствие поля у старых конфигураций означает пустой набор проверок. На запуске фиксируются исходники, SHA256 и параметры всех выбранных проверок. Изменение скрипта или конфигурации не меняет уже созданный прогон. Общий выход ограничен 100 000 строк; превышение отклоняется до публикации, поэтому HTML содержит весь принятый результат.

```python
def run(mart, params):
    apps = mart.app_ids(diff_flag=1)
    return [{"LABEL": "Есть изменения", "SOURCE": "AFTER", "ARGUMENT": "",
             "CNT": len(apps), "TOTAL": mart.total_apps(),
             "METRIC": len(apps) / mart.total_apps() if mart.total_apps() else 0,
             "APP_IDS": apps[:20], "RESULT": "FAIL" if apps else "PASS",
             "CONFIDENCE": "HIGH"}]

CHECK = {"id": "changes", "label": "Есть изменения", "params": {}, "entrypoint": run}
```

`MartAPI.rows(**filters)` возвращает строки сравнения; `count` считает строки, `app_ids` возвращает отсортированный уникальный набор заявок. `segments()` читает слой разрезов, `total_apps()` — число заявок. Поддержаны `path` (строка или список), `path_prefix`, `key`, `array_key`, `diff_flag`, `change_type` (строка или список), `value_before`, `value_after`, `app_ids`; фильтры соединяются через И. Строки содержат значения канонической витрины (`true`, `false`, `NULL`), а не Python bool/null вместо них.

В одном изолированном задании строится индекс SQLite в памяти поверх NDJSON; все проверки этого запуска используют этот индекс. Вход читается лениво, `count` и `app_ids` не сканируют JSON заново. Сначала применяются параметры `CHECK.params`, затем параметры сохранённой процедуры и выбранной проверки в конфигурации. Ошибка исполнения или нарушение выходного контракта завершает прогон ошибкой с диагностикой; частичный отчёт не публикуется.

Каждая выходная строка содержит `LABEL`, `SOURCE`, `ARGUMENT`, `CNT`, `TOTAL`, `METRIC`, `APP_IDS`, `RESULT` и `CONFIDENCE`. Система добавляет идентификатор строки и происхождение проверки. `RESULT` допускает PASS/FAIL, `CONFIDENCE` — HIGH/LOW. `APP_IDS` может содержать только заявки данного прогона. LOW — слабый сигнал, поэтому отображается бледнее обычного FAIL. CNT может быть больше длины APP_IDS из-за ограничения выборки внутри скрипта.

## Отчёт и сводная — этап 5

Сводная группирует сохранённые данные SQL-запросом по выбранным полям строк и колонок. Для каждой ячейки вычисляется `COUNT(DISTINCT app_id)`; суммы соседних ячеек не используются как число уникальных заявок. Переход к заявкам передаёт тот же набор фильтров и значения измерений выбранной ячейки в `/query/apps`.

Ссылки вида `/?run=<id>&tab=report`, `tab=checks` и `tab=pivot` открывают нужный раздел после входа. HTML-экспорт содержит все строки проверок, встроенное оформление, экранированные пользовательские значения и ссылку обратно в сводную. Для его локального просмотра сервер не требуется; переход в приложение требует работающего сервера и входа владельца. Файл HTML содержит результаты прогона — доступ к скачанному файлу определяется тем, кому пользователь передаёт файл.

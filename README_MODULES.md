# Decision Lens — модули и принципы работы

Приложение сравнивает готовые JSON-ответы системы принятия решений (СПР): **BEFORE** — действующая версия, **AFTER** — тестируемая. Оно показывает, какие значения изменились, у каких заявок сменилось решение и какие автоматические проверки сработали.

Основная логика — C++20, пользовательские процедуры — Python, интерфейс — React/TypeScript, постоянное хранилище — PostgreSQL.

## Общий путь данных

```text
JSON BEFORE + AFTER
       ↓
Загрузка и проверка пар заявок
       ↓
1. Нормализация → вертикальная витрина UNION
       ↓
2. Сравнение + разрезы по заявкам
       ↓
3. Агрегация: группы и количество уникальных заявок
       ↓
4. Python-проверки: единая таблица PASS / FAIL
       ↓
5. Отчёт → сводная → список заявок → конкретный атрибут
```

## Реализованные модули

### Загрузка и конфигурации

Принимает встроенный датасет либо папку с `manifest.json` и ответами двух срезов. Проверяет JSON, совпадение идентификаторов, наличие обеих сторон и отсутствие дублей. В конфигурации выбираются процедуры, правила массивов, исключаемые поля, бакеты, измерения агрегации и проверки.

При создании запуска фиксируются **снимки конфигурации, исходников и параметров**. Последующее изменение кода не меняет уже созданный запуск.

### 1. Нормализация

Превращает вложенный JSON в плоские строки: заявка `APP_ID`, путь `PATH`, ключ элемента массива `ARRAY_KEY`, значение, тип и срез `SOURCE`.

Массивы сопоставляются по выбранным полям, значению или позиции. Поэтому перестановка объектов с устойчивыми идентификаторами не создаёт ложных изменений. Отсутствующее поле, `null`, `false`, число `0` и строка `"0"` различаются.

Строки BEFORE и AFTER объединяются **вертикально**, с сохранением `SOURCE`. Это технический UNION.

### 2. Сравнение и разрезы

Используется **сортировка и последовательное слияние**: внутри каждой заявки строки сопоставляются по `PATH + ARRAY_KEY`. Сравниваются исходные типизированные значения.

| Результат | Значение |
|---|---|
| `SAME` | Значение не изменилось |
| `VALUE_CHANGED` | Значение или его тип изменились |
| `ATTRIBUTE_NEW` | Атрибут появился |
| `ATTRIBUTE_LOST` | Атрибут исчез |

Отдельно формируется контекст заявки: продукты, партнёр, модели, пороги, решения и признаки изменений. Эти разрезы используются в фильтрах и группировках.

### 3. Агрегация

Группирует данные по выбранным измерениям: пути атрибута, значению или бакету, срезу, продукту и другим разрезам. Для каждой группы сохраняет `CNT` и связь с заявками.

**CNT — число уникальных заявок, а не число строк.** Если у заявки изменились десять атрибутов, в одной группе она считается один раз. Бакеты упрощают группировку чисел; определение различий сохраняет точность исходных значений.

### 4. Автоматические проверки

Включены пять скриптов из задания: падение Approval Rate продукта, появление/исчезновение атрибутов, изменение внешнего скора, исчезновение стоп-фактора и смена целевой модели.

Пользователь может подключить свой `.py` или написать проверку в редакторе Monaco. Скрипт экспортирует объект `CHECK` с функцией `run(mart, params)` и возвращает строки результата.

`MartAPI` предоставляет выборки, количество строк, уникальные заявки и разрезы. Для повторных запросов worker строит **индекс SQLite в памяти**. Основные данные и результаты остаются в PostgreSQL.

`PASS/FAIL` — результат бизнес-проверки; `LOW` — слабая уверенность и бледная подсветка. `APP_IDS` может быть ограниченной выборкой, поэтому его длина не обязана равняться `CNT`.

### 5. Отчёты и сводная

Итоговый экран показывает охват изменений, смены решений и результаты проверок. В сводной пользователь меняет строки, колонки и фильтры. Группировка выполняется SQL по сохранённой витрине, без повторного разбора JSON.

Нажатие на число открывает заявки группы, затем — значения BEFORE/AFTER конкретной заявки. Соседние ячейки могут содержать одну заявку, поэтому их суммы не считаются общим числом затронутых заявок.

Отчёт можно открыть по ссылке и скачать в HTML. HTML содержит все строки проверок и ссылку обратно в приложение.

## Служебные модули

| Модуль | Принцип работы |
|---|---|
| HTTP API и управление запусками | C++/Drogon принимает запросы; обработка выполняется в фоновой очереди. Доступны статус, прогресс, журнал и отмена. |
| Python worker | Получает задания через файловую очередь в формате NDJSON. Запускает код отдельным процессом с лимитами времени/памяти и ограничениями Linux Landlock/seccomp. |
| PostgreSQL | Хранит пользователей, конфигурации, запуски, витрины, факты, результаты проверок и связи с заявками. Для массовой записи используется COPY. |
| Авторизация | Пользователи работают со своими конфигурациями и запусками; сервер проверяет владельца при доступе к данным. |
| Веб-интерфейс | React/TypeScript отображает результаты API; TanStack Query управляет загрузкой данных, Monaco — редактированием Python. |
| Docker Compose | Собирает backend и frontend внутри контейнеров и запускает четыре сервиса: backend, frontend, PostgreSQL и worker. |

Ошибка Python-кода или нарушение контракта переводит запуск в `failed`, а диагностика сохраняется в журнале. Это отличается от бизнес-результата `FAIL`. Готовые данные и отчёты доступны только после полного завершения запуска (`completed`).

## Где искать реализацию

| Файл или каталог | Что находится внутри |
|---|---|
| `backend/src/core.cpp` | Нормализация, сравнение, разрезы и агрегация |
| `backend/src/server.cpp` | HTTP API, авторизация и очередь запусков |
| `backend/src/storage.cpp` | PostgreSQL, сохранение и SQL-группировки |
| `backend/src/stage_executor.cpp` | Передача заданий из C++ в Python worker |
| `backend/src/reports.cpp` | Проверка результатов checks и HTML-экспорт |
| `python-worker/runner/` | Супервизор, песочница, исполнение процедур и MartAPI |
| `python-worker/procedures/`, `python-worker/checks/` | Python-шаблоны и пять выданных проверок |
| `frontend/src/` | Экраны приложения, редактор, отчёт и сводная |
| `database/migrations/` | Структура таблиц и индексов |

## Запуск и первый просмотр

Из папки проекта, где находится `docker-compose.yml`:

```bash
docker compose up -d --build
```

Открыть **http://localhost:8088**, зарегистрироваться, создать конфигурацию, выбрать датасет и проверки, запустить обработку. После завершения пройти цепочку **отчёт → сводная → число → заявка → атрибут**. Компилятор на хосте не требуется; `start.sh` — необязательная обёртка для Docker Compose.

LLM-анализ и ZKP не реализованы. Целевая скорость полного цикла 30 секунд пока не достигнута; подробности замеров — в `docs/VALIDATION.md`. Точные схемы данных и API описаны в `docs/CONTRACTS.md`.
